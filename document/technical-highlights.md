# 技术难点与创新点

本文档说明 DL/T 645-2007 电能表采集项目在设计与实现过程中面临的主要技术挑战，以及相对同类采集方案的差异与亮点。架构与模块细节见 [project.md](project.md)、[design.md](design.md)。

---

## 一、技术难点

### 1.1 国标协议实现的正确性与完备性

DL/T 645-2007 并非简单的「发请求、读应答」，实现上有多处易错点：

| 难点 | 说明 |
|------|------|
| **BCD 字节序** | 地址域、数据域均为 BCD，且**低字节在前**；与常规大端整数、字符串地址表示不一致，编解码须严格按规约处理。 |
| **数据域 ±0x33** | 传输时逐字节加 0x33、接收后减 0x33，用于避免数据中出现 `0x68`/`0x16` 等定界符；编解码器须对「原始数据」与「线路上数据」分层处理。 |
| **校验和范围** | 校验为从**第一个** `0x68` 起至数据域最后一字节的模 256 和；起止位置算错会导致合法帧被判无效。 |
| **控制码与异常应答** | 除正常应答 `0x91` 外，须识别异常应答 `0xD1` 及错误码，并与「超时」「地址不匹配」等传输层错误区分。 |
| **前导符** | 发送侧通常带不少于 4 字节的 `0xFE` 唤醒从站；接收侧需跳过可变长度前导后再定位帧头。 |

协议层任何一处偏差都会导致现场表现为「偶发超时」「数值错乱」或「全部表无数据」，且难以用日志一眼定位，因此需要可重复的单元测试覆盖边界用例。

### 1.2 串口字节流上的帧定界与超时

串口 `read()` 返回的是**任意长度字节块**，不是「一帧一包」：

- **半包**：一次读到的数据不足一整帧，须累积到 `recv_buffer_` 再尝试解析。
- **粘包**：一次读到多帧或「残留 + 新帧」，须在解析成功后按 `bytes_consumed` 消费缓冲区，避免重复解析或错位。
- **噪声与假帧头**：总线上可能出现与 `0x68` 相似的干扰，仅靠单字节匹配不可靠，需结合长度域 `L`、校验和、结束符 `0x16` 联合校验。
- **双层超时**：`IChannel::receive` 为单次读超时，`FrameTransceiver::receive_frame` 为**整帧**超时；二者配合才能在「表计无响应」时及时失败，又能在表计响应较慢时收齐数据。

`FrameTransceiver` 是传输层与协议层的衔接点，也是现场稳定性最敏感模块之一。

### 1.3 RS-485 多表总线与轮询时序

本程序面向 **RS-485 总线挂多块电表** 的场景：

- **半双工**：同一时刻总线仅允许一个方向传输；发送后须留出从站处理与线路稳定时间再读应答，否则易丢首字节或校验失败。
- **低波特率**：规约现场常用 **2400 bps、8E1**，单帧交互耗时长，轮询表数 × 采集项数会线性拉长一轮周期。
- **地址与接线**：表计通信地址须与配置一致；总线终端电阻、共地、A/B 反接等问题在软件层只能体现为超时或乱码，需通过细粒度错误码辅助排查。

`Scheduler` 按「电表 × 数据项」顺序轮询，轮询间隔与单次读超时共同决定总线负载，需在配置中权衡。

### 1.4 可配置数据项与表计差异

不同厂家、型号的电能表对**数据标识（DI）**、数据长度、小数位、是否支持某项的支持程度不同：

- 配置中 `di`、`length`、`decimal` 必须与表计规约一致，否则正常应答也可能无法解码，或触发 `0xD1` 异常应答。
- 应答帧数据域前 4 字节为 DI，须与请求 DI 比对（`MeterReader::validate_response`），防止总线上其他设备串扰或残留帧被误用。
- `DataItem::decode_value` 需按配置的小数位将 BCD 转为物理量，同一 DI 在不同表型上长度可能不同，不宜写死在代码里。

将采集项元数据外置到 YAML，是降低现场适配成本的关键，但也对配置校验（`Config::validate`）提出更高要求。

### 1.5 嵌入式 OpenWrt 网关上的交叉编译与运行

目标环境为 **aarch64 + musl** 的 OpenWrt 网关，与开发机 x86_64 不同：

- 使用 `openwrt-gcc-8.3.0` 交叉工具链，第三方依赖（yaml-cpp、spdlog）须能在交叉编译下正确链接。
- **单元测试仅在宿主机构建**，网关只部署 `dlt645_collector` 单二进制，协议正确性必须在开发阶段通过 TDD 保证，现场难以做自动化回归。
- 资源受限：单进程、无数据库，日志与配置即主要可观测手段。

### 1.6 缺乏专用硬件时的质量保障

真实表计与 RS-485 采集器不易接入 CI，若业务逻辑与串口强耦合，则协议回归只能依赖人工抄表：

- 通过 **`IChannel` 抽象**，用 `MockChannel` 注入预定字节流，可测 `FrameTransceiver`、`MeterReader` 全路径。
- 协议层（`BcdCodec`、`FrameCodec`、`DataItem` 等）保持**纯函数/无 IO**，便于构造向量用例（合法帧、坏校验、短帧、多前导符等）。

难点在于：测试用例须覆盖规约边界，且 Mock 行为要贴近真实「分段到达」的接收模式。

## 二、创新点说明

### 2.1 总体界定

本项目**未对 DL/T 645-2007 标准本身做修改或扩展**，也未引入新的通信机制，因此**不属于协议或学术意义上的「创新」**。  
在电力行业采集领域，基于 645 规约的读表程序已有大量成熟实现（含商业采集器、开源工具等）。

本项目的价值主要体现在：**在资源受限的 OpenWrt 网关上，用现代 C++ 工程方法把协议正确性、可配置性与可测试性做扎实**，下列为相对「脚本拼凑、无测试、采集项写死」方案的差异点，可称为**工程实践亮点**。

### 2.2 工程亮点（可视为项目特色）

| 亮点 | 说明 |
|------|------|
| **TDD 驱动协议栈** | 自底向上：BcdCodec → Frame/FrameCodec → DataItem → 传输与应用；先写失败测试再实现，降低 645 实现错误流入现场的概率。 |
| **传输层可替换** | `IChannel` 隔离 termios 与业务；协议层、读表逻辑不依赖真实 `/dev/tty*`，利于自动化回归与后续扩展（如 TCP 透传通道）。 |
| **采集项配置化** | 电表列表、DI、长度、小数位、单位、轮询周期均由 YAML 定义，扩展采集量无需改代码、仅改配置并做校验。 |
| **细粒度错误语义** | `MeterReader::ErrorCode` 区分发送失败、超时、地址不匹配、异常应答、DI 不匹配、解码失败，便于日志排错与上层对接。 |
| **三层解耦架构** | 协议 / 传输 / 应用职责清晰：协议层不依赖串口；`ResultReporter` 与采集逻辑解耦，便于更换输出方式。 |
| **宿主机测、网关跑** | 交叉编译与本地 GoogleTest 分离：开发机保证质量，网关仅部署轻量二进制 + 配置，符合边缘设备运维习惯。 |

### 2.3 与常见方案的对比（简要）

| 维度 | 常见简易方案 | 本项目取向 |
|------|----------------|------------|
| 协议实现 | 脚本或单文件硬编码 | 独立协议层 + 单测覆盖 |
| 采集项 | 写死在源码 | YAML + `DataItem` 元数据 |
| 测试 | 现场人工对表 | Mock 通道 + 分层单测 |
| 部署 | 同机编译或手工拷贝 | 固定 OpenWrt 工具链 + `build-cross` 脚本 |
| 错误处理 | 统一「失败」 | 分类型错误码 + 结构化日志 |

## 三、难点与模块对应关系

| 技术难点 | 主要承担模块 |
|----------|----------------|
| BCD / ±0x33 / 校验和 | `BcdCodec`、`FrameCodec` |
| 帧定界、粘包、整帧超时 | `FrameTransceiver`、`SerialPort` |
| 读表交互与应答校验 | `MeterReader` |
| 表计与采集项差异 | `Config`、`DataItem`、YAML 配置 |
| 多表轮询与总线负载 | `Scheduler` |
| 交叉编译与网关部署 | `cmake/openwrt-aarch64.cmake`、`scripts/build-cross.sh` |
| 无硬件测试 | `IChannel`、GoogleTest、`tests/test_*.cpp` |

## 四、后续可深化方向（非当前创新点）

以下能力若实现，可进一步增强竞争力，但**当前版本尚未作为已交付创新点**：

- 按表型加载 DI 模板或规约插件，减少手工配置 `length`/`decimal`。
- 总线冲突检测、自动重试与指数退避策略。
- 采集指标导出（Prometheus）或网络上报，与现有日志输出并列。
